# 🎭 入局 MYSTERY·STUDIO — 开场前异常改期 / 候补递补 / 多店资源原子调度

剧本杀门店开场前异常处置系统：当门店在剧本开场前发生**主持人缺勤、场次延迟、房间不可用**时，系统不是简单取消场次，而是统一统筹**已报名玩家、候补队列、主持人排班、房间资源、剧本库存与会员权益**，支持店长发起四类改期方案（同日换场 / 跨店迁移 / 全额退款 / 保留权益待补位），给出可解释候选；确认迁移时对**原场次名额、目标房间、主持班次、剧本库存一次性锁定**，并发确认中任一资源失效即**整体回滚**，保证不超卖、不重复退款、不出现“已扣权益却无座位”。

技术栈：**React 18 + TypeScript + Vite + Zustand（persist 本地持久化）**，纯前端单页应用（前端项目，无 Swagger 要求），Nginx 托管静态资源，无外部数据库依赖，演示数据内置、可一键重置。

## 原始需求

> 门店在剧本开场前发生主持人缺勤、场次延迟或房间不可用时，系统需同时处理已报名玩家、候补队列、主持人排班、房间资源、剧本库存和会员权益，而不是只把场次改为取消。店长可发起改期方案：同日换场、跨店迁移、全额退款或保留权益待补位；每种方案都要先计算玩家可接受时段、角色偏好、拼车/同行关系、会员优先级、房间容量与主持人技能匹配，并给出可解释的候选安排。确认迁移时需对原场次名额、目标房间、主持人班次和剧本库存做一次性锁定；若其中任一资源在并发确认中失效，系统必须整体回滚并保留原场次可售/候补状态，不能出现玩家已扣权益却无有效座位。候补递补要遵循公开的优先级规则，并区分“同意自动补位”“仅接受指定时段”“超过时限未响应”；店长手工调整必须填写原因且不能绕过容量和角色人数约束。玩家端需实时看到方案、确认倒计时、权益变化和失败原因，店长端需看到冲突资源、候补排序和需人工介入事项。最终应形成场次事件时间线，覆盖异常触发、方案计算、玩家确认、资源锁定、退款/补偿和排班变更，保证重复确认、延迟通知和多店同时抢占不会造成超卖、重复退款或角色配置失衡。

## 一键启动（Docker Compose，推荐）

前置：宿主已安装 Docker Engine（含 compose 插件）。

```bash
cd 111-feature-4-b
cp .env.example .env          # CC_PUBLISH_PORT 默认 3211，可改
docker compose up -d --build
docker compose port app 8080  # 查看实际映射端口
# 浏览器访问 http://localhost:3211 （或上一步输出的端口）
```

停止：

```bash
docker compose down
```

- compose 只发布应用端口，容器内固定 8080；非 root（uid 101）运行，镜像内置 `/healthz` HEALTHCHECK。
- 数据保存在浏览器 LocalStorage（Zustand persist），右上角「↺ 重置演示」可恢复内置数据。

### 推荐验证路径（约 5 分钟）

1. 以**店长**进入「异常改期中心」→ 打开预置异常单 `dc-1` → 点「🧮 计算候选安排」。
   - 可行：**跨店并入静安 19:00**（适配分最高）、**同日换场 21:30**（可换至唐风大厅+周岩/小鹿）、**全额退款**、**保留权益待补位**。
   - 不可行候选用红条标明冲突：15:30 熟练主持均有档期冲突、静安 21:30 唯一盒装与 19:00 场时间重叠（一店一盒）。
2. 选择「跨店迁移：并入静安分店 19:00」→ 玩家确认表面板出现 **30 分钟倒计时**（可点「模拟倒计时结束」跳过）。
3. 一组点「同意」、一组点「拒绝」→ 预检五阶段全绿后点「⚡ 一次性锁定并原子确认」：
   - 目标场次变 5 人（未超卖）、拒绝组 2 笔全额退款流水（可到「收退款」核对幂等键）、原场次转「改期待补」。
4. 重置演示后重试：在确认前勾选「🧪 抢占目标房间/调走主持/借走盒装」任一开关 → 再原子确认 → 看到**整体回滚**（玩家未扣费、原场次仍可售/候补、方案保留具体失败原因）；解除抢占后可重新计算并提交成功。
5. 再次提交已执行方案 → 弹窗提示**重复确认被幂等拦截**，退款/座位不重复。
6. 「候补队列」面板核对公开排序：苏晴 215 > 王胖子 100 > 吴迪 50 > 赵雨桐 25；对「改期待补」场次点「按公开规则自动递补」；手工递补超容量时被拦截（必须填原因）。
7. 切**玩家**角色 →「我的拼场」可看到方案卡、倒计时、同意/仅此时段/拒绝按钮与权益说明；「候补与我的权益」可改自动补位策略、接受时段、查看权益券；右上角 🔔 可看实时通知（含失败原因）。

## 需求覆盖对照

| 需求点 | 实现位置 |
| --- | --- |
| 不只取消场次：统筹玩家/候补/排班/房间/库存/权益 | 异常单保持原场次名额冻结；`DisruptionCase` + 四类方案；原场次提交后转「改期待补」仍可售/候补 |
| 四类方案 + 可解释候选（时段/角色偏好/同行/会员/容量/主持技能） | `disruption.ts/buildPlans`：逐候选输出 `fit`（拼车整组、角色偏好、房间容量、主持熟练度、盒装库存、通勤补偿）与 `blockers` |
| 一次性锁定四类资源 | `store.ts/commitPlan`：同一次状态更新内建立「原场次名额/目标房间/主持班次/剧本库存」锁并生效，带事务号与锁台账 |
| 任一资源并发失效 → 整体回滚，保留原场次可售/候补 | 提交前 `validatePlan` 五阶段终检；失败则方案「已回滚」、异常单「执行失败已回滚」、无任何副作用；`SimClaim` 模拟多店抢占 |
| 不超卖 / 不重复退款 / 不扣权益无座位 | 目标余量按房间容量与角色上限计算；流水带 `idemKey`（`case-refund:<case>:<player>` 等）；53 项不变量校验覆盖 |
| 候补公开优先级 + 三种响应策略 | 金卡+100/银卡+60、到店×5、预付+50、登记次序+0/20/40…；同意自动补位 / 仅接受指定时段 / 暂不自动补位；邀约倒计时超时顺延 |
| 超时未响应 | `expirePlanResponses`：不随迁不占座，已付款转「全额权益保留」券；通知与时间线留痕 |
| 手工调整必须填原因且不得绕过容量/角色人数 | `manualAdjust/assignRoom/assignHost`：原因必填，校验容量、房间故障、跨店归属、主持请假/跨店资质；`promoteWaitlistManual` 校验容量与角色配置 |
| 玩家端实时方案/倒计时/权益/失败原因 | 我的拼场方案卡（秒级倒计时、三种响应、回滚原因、执行结果）；候补中心邀约倒计时；权益券列表；通知铃铛（去重 `dedupKey`） |
| 店长端冲突资源/候补排序/人工介入 | 候选红条冲突、提交预检徽章、候补表（分数+规则解释）、看板顶部「需人工介入」卡、回滚原因 |
| 场次事件时间线全链路 | `SessionEvent`：异常触发→方案计算→玩家确认→资源锁定→资源失效→资源回滚→退款/补偿→排班变更→执行成功 |
| 重复确认 / 延迟通知 / 多店抢占安全 | 响应与提交幂等；通知 `dedupKey` 去重；确认/锁 TTL 由 `sweepDeadlines` 扫描；抢占模拟终检失败整体回滚 |
| 多店与剧本盒装库存 | `StoreInfo`/`ScriptCopy`；房间、主持（含 crossStore）、盒装均按门店归属；跨店迁移锁目标店盒装 |

  pages/
    DisruptionPages.tsx        # 店长：异常改期中心（候选/确认/抢占模拟/候补/手工调整/锁/时间线）
    PlayerDisruptionPages.tsx  # 玩家：方案确认、候补登记与邀约、权益券
    PlayerPages.tsx / SchedulePages.tsx / SessionsPage.tsx / DashboardPage.tsx / …
verify/
  verify.ts                # 53 项核心不变量（Node 直跑真实 store）
  ui-smoke.tsx             # 五角色 + 异常中心渲染冒烟
Dockerfile / docker-compose.yml / nginx.default.conf
